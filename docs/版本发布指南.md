# 版本发布指南

维护者：singerTang

## 版本规则

- package.json 是软件版本号的唯一来源，package-lock.json 的根版本同步更新。
- 修复问题增加末位，如 1.1.0 → 1.1.1；兼容的新功能增加中位，如 1.1.0 → 1.2.0；不兼容改动增加首位。
- 侧栏显示服务端启动时加载的版本，修改版本后必须重启。它不能证明所有前端文件均已上传，部署时仍需完整核对文件。
- 图标自身的版本字段不属于软件发布版本管理。

## 发布步骤

1. 检查 git status 和全部差异，确认本次发布内容，不纳入密钥和业务数据。
2. 后续升版使用 npm version patch --no-git-tag-version 或 npm version minor --no-git-tag-version，同步两个包清单；本次已设置 1.1.0，无需再执行升版。
3. 完善更新日志，执行 npm test、npm run test:trash 和相关浏览器专项测试，检查 git diff --check。回收站测试在 Windows 使用已安装的 Edge，并使用独立临时数据库。
4. 明确选择文件提交，确认工作区没有遗漏的发布改动。将更新日志中的待发布改为正式日期后提交，再创建 git tag -a v1.1.0 -m "发布 v1.1.0"。标签必须对应实际发布源码；未经验证不创建标签。
5. 从该标签制作源码发布包，文件名包含版本；需要同步远程时，显式推送对应提交与标签。本指南不自动提交或推送。

## 本次 1.1.0 服务器更新

累计运行文件清单：

```text
package.json
package-lock.json
server.js
db.js
lib/trash.js
public/index.html
public/app.js
public/style.css
public/selection-controls.js
public/trash.js
```

1. 使用 pm2 list、pm2 describe <实际进程名> 确认进程与工作目录，记录旧版本并备份现有代码。
2. 停止对应进程后，备份实际 SQLite 数据目录及 uploads，保留 .env；如设置 DB_PATH，以实际数据库路径为准。停服务备份可避免复制到不一致的数据库及图片快照。
3. 只覆盖清单中的运行文件。不要覆盖 data、uploads、.env、node_modules。本次无依赖变化，不需要重装依赖。
4. 启动实际进程，旧库将自动新增 deleted_at、purge_after、deleted_folder_path、deleted_category 四个字段、到期索引和 app_settings 表。原图标不移入回收站。检查 PM2 日志及 /api/version 返回 1.1.0，浏览器 Ctrl+F5 后确认侧栏版本和图标展示，再验证搜索、分类、批量选择及回收站恢复。
5. 将服务器地址、部署时间、版本、Git 提交号及备份位置记录在团队部署记录中。

## 回退

- 本次增加回收站数据状态，旧代码不会排除已删除图标，直接换回旧代码会使回收站图标重新出现在普通图库，且旧删除接口会直接清理文件。不能仅覆盖旧代码回退。
- 如需回退，先停服务并完整备份当前数据库与 uploads；由维护人员核对升级后的新增数据和回收站记录，再制定兼容回退。仅在明确接受丢弃升级后变更时，才能恢复升级前的整套代码、数据库与图片快照。
- 不因代码回退直接恢复旧数据库，否则会丢失更新后新增的业务数据。
- Git 标签只保存源码，不能恢复数据库或上传文件。回收站不替代独立备份，也无法恢复此前已经彻底删除的图片。

## 回收站运行规则

- 入口位于左下侧栏，默认保留 30 天，可设置 7、30、60、90 天。设置是全库共享，保存后只影响之后移入的图标。
- 每条记录保存独立到期时间。恢复保留原上传时间，再次移入重新计时；原分类或文件夹已删除时，恢复为未分类或无文件夹归属并提示。
- 自动清理在服务启动时及每小时执行，无需配置 Linux 定时任务。关机期间不会执行，重启后补清到期项。
- 彻底删除及清空不可恢复。文件删除失败时保留该条记录，自动任务下次重试；共享文件仅在最后一条引用删除时清理。
- 普通列表、分类关联、统计、批量操作及 JSON 导出排除回收站。完整备份数据库与 uploads 才能包含回收站记录和图片。
